# Методичка к защите лабораторной №3

Вариант: Spring Boot + Hibernate/JPA. Первый участник отвечает за студентов и хранение данных, второй — за пользователей, JWT и права доступа. Оба должны понимать запуск и общий путь запроса.

## 1. Что делает приложение

Приложение хранит студентов общежития в реляционной БД H2. Доступ к API требует входа. USER читает студентов, ADMIN дополнительно создаёт, изменяет и удаляет их. Есть регистрация, вход, access- и refresh-токены.

Все Java-файлы находятся в `src/main/java/ru/studentlab/students`. Поэтому в таблицах ниже пути приведены относительно этой папки.

Общий путь защищённого запроса:

```text
Браузер / Postman
  → Spring Security: проверка JWT и прав
  → Controller: HTTP-запрос
  → Service: действия и проверки
  → Repository: запрос к БД
  → Hibernate → H2
  → DTO → JSON-ответ
```

`SecurityConfig` задаёт правила заранее при запуске; при обработке запроса их применяют фильтры Spring Security. Если токен неверный или прав недостаточно, метод контроллера не выполняется.

## 2. Коротко для человека, знакомого с C++

- `class`, поля, методы, конструкторы и `public/private` имеют знакомый смысл.
- `new` создаёт объект. В Java не нужно вручную вызывать `delete`: память освобождает сборщик мусора.
- `String` — строка; содержимое сравнивается через `.equals()`, а не `==`.
- `List<Student>` похож на список/vector, `Map<String, String>` — на словарь.
- `Integer` и `Boolean` могут быть `null`. Это позволяет отличить отсутствие поля от 0 и false.
- `enum Role` — перечисление двух значений: USER и ADMIN.
- `@...` — аннотация, то есть пометка для библиотеки. `@Entity` связывает класс с таблицей, `@GetMapping` — метод с HTTP-адресом.
- Spring создаёт объекты сервисов и передаёт зависимости через конструктор. Это Dependency Injection. Не нужно самому создавать все сервисы в `main`.

### Что знать о данных

У студента есть имя, группа, ИСУ, общежитие, комната, дата, иностранный статус и заметки. В БД также есть внутренний `id`. В URL используется ИСУ. При исправлении ИСУ внутренний id остаётся прежним.

ИСУ уникален. Сервис заранее проверяет его занятость, а ограничение UNIQUE в БД защищает и от двух одновременных запросов. Обязательные столбцы имеют NOT NULL.

`Student` — сущность Hibernate, `StudentDto` — обычный объект для передачи данных. В ответе нет внутреннего id. Изменение сущности БД не должно автоматически менять контракт API.

Основные проверки: ФИО содержит минимум два слова из букв; группа — буква и четыре цифры, первая цифра не ноль; ИСУ 100000–999999; общежитие 1–100; комната — 2–4 цифры и необязательная буква; дата должна существовать; foreigner — логическое значение. Проверки браузера удобны, но сервер проверяет данные самостоятельно.

### Как разобрать создание студента

1. Браузер передаёт POST `/api/requests` с JSON и access-токеном.
2. Security пропускает только ADMIN.
3. `StudentController.create` вызывает `StudentService.create`.
4. `StudentValidator.read` проверяет поля.
5. Сервис проверяет занятость ИСУ, создаёт Student и копирует поля.
6. Репозиторий вызывает `persist` и `flush`; Hibernate выполняет INSERT.
7. Контроллер возвращает DTO, статус 201 и заголовок Location.

### PUT, PATCH и транзакции

PUT заменяет полную запись и требует все обязательные поля. Если заметка не передана, она очищается. PATCH начинает с копии текущих данных и заменяет только присланные поля. Например, `{"room":"225"}` не стирает имя и группу.

`@Transactional` объединяет изменение в одну операцию. При исключении изменения отменяются. Основные свойства транзакции: атомарность, согласованность, изолированность, долговечность — ACID. Нельзя объяснять транзакцию просто как «сохранение файла».

### Поиск и страницы

Фильтры объединяются через И. Текст ищется по части значения без учёта регистра, foreigner сравнивается точно. `dormitory` — старое название параметра dorm, сохранённое для frontend. QUERY принимает те же фильтры в JSON.

В репозитории запрос собирается из разрешённых имён полей. Значения передаются через `setParameter`, а не вставляются в строку. `%` означает любую последовательность символов в LIKE; пользовательские `%`, `_` и обратная косая черта экранируются, чтобы искаться буквально.

Сортировка тоже допускает только поля студента. `cast(... as string)` нужен для поиска по части числа или даты. `where 1 = 1` позволяет удобно добавлять условия через AND.

`page` начинается с 0, `size` находится в диапазоне 1–100. `setFirstResult` задаёт смещение, `setMaxResults` — максимум записей. Отдельный COUNT получает общее количество. БД выполняет фильтрацию и пагинацию. Без page/size весь список возвращается для совместимости с прошлой лабораторной.

### Регистрация и BCrypt

Регистрация проверяет имя 3–40 символов, формат email и пароль 6–40 символов, максимум 72 байта UTF-8 для BCrypt. Email приводится к нижнему регистру. Имя и email уникальны также в БД.

Публичный метод регистрации всегда передаёт Role.USER. Присланное клиентом поле role не назначает ADMIN. Администратор создаётся отдельным инициализатором из `.env`.

BCrypt вычисляет хеш с солью. Соль входит в результат; одинаковые пароли не обязаны давать одинаковые хеши. На входе `matches` проверяет пароль относительно сохранённого хеша. Расшифровки пароля в проекте нет. Хеш и исходный пароль не выдаются в API.

### Вход и защищённый запрос

1. POST `/api/auth/login` получает имя и пароль.
2. `AuthService` находит пользователя и проверяет BCrypt-хеш.
3. `JwtService` создаёт access и refresh.
4. Клиент отправляет access в `Authorization: Bearer ...`.
5. `JwtFilter` проверяет подпись, срок и тип access, читает имя.
6. Пользователь и его актуальная роль читаются из БД.
7. Фильтр создаёт Authentication с ROLE_USER или ROLE_ADMIN.
8. Spring Security разрешает или запрещает операцию по правилам SecurityConfig.

Для неверного имени и неверного пароля возвращается одинаковое сообщение. В логах нет паролей и полных токенов.

### Что знать о JWT

JWT содержит три части: заголовок, payload и подпись. В payload проекта есть `sub` — имя, `type` — access/refresh, `iat` — время выдачи и `exp` — окончание действия. Payload можно прочитать: подпись не означает шифрование. Пароль туда не кладётся.

Ключ подписи находится в окружении, а не в Java-коде. В данном HMAC-варианте нужен ключ минимум 32 байта. Изменённый или просроченный токен не принимается. Просто декодировать payload недостаточно — нужна проверка подписи и срока. Это делает библиотека JJWT.

По умолчанию access действует 15 минут, refresh — 7 дней. Настройки в `.env` заданы в миллисекундах; `expiresIn` в ответе — в секундах.

### Refresh и выход

POST `/api/auth/refresh` принимает refreshToken. Сервис проверяет подпись, срок, тип refresh и существование пользователя, затем выдаёт новую пару. Access вместо refresh не подходит. Refresh вместо access не открывает студентов.

`js/storage.js` при 401 один раз пытается обновить access и повторить запрос. Если обновление не удалось, пользователь возвращается на вход. Токены находятся в sessionStorage вкладки.

Выход удаляет токены из браузера. В минимальном варианте нет списка отозванных токенов: уже выданный JWT действует до своего срока, а прежний refresh не аннулируется при обновлении. Не нужно утверждать на защите, что сервер делает немедленный отзыв JWT.

### Таблица прав

| Операция | Без токена | USER | ADMIN |
|---|---|---|---|
| Регистрация, вход | Разрешено | Разрешено | Разрешено |
| Обновление | Нужен действующий refresh в теле | Нужен refresh | Нужен refresh |
| GET списка/студента, QUERY | 401 | Разрешено | Разрешено |
| POST/PUT/PATCH/DELETE студентов | 401 | 403 | Разрешено |
| GET `/api/auth/me` | 401 | Имя и роль | Имя и роль |

Для запросов входа и refresh заголовок Authorization не требуется. Если он всё же передан и содержит неверный access, фильтр также может вернуть 401.

401 означает отсутствие действительной аутентификации; 403 — пользователь определён, но операция ему не разрешена. Эти ответы формируются до MVC-контроллера, поэтому `SecurityErrors` нужен отдельно от `GlobalExceptionHandler`.

## 5. Что взято из кода второго участника

Сохранены User, Role, LoginRequest, RegisterRequest, TokenResponse, UserRepository и логика JwtService на JJWT. Файлы перенесены в общий пакет `ru.studentlab.students`, имена приведены к именам Java-классов. Lombok заменён обычными методами, record — простыми классами. Модель User хранится в таблице app_users; имя таблицы не совпадает с SQL-словом USER.

В переданных файлах не было контроллера авторизации, сервиса регистрации/входа и защиты маршрутов. Поэтому добавлены AuthController, AuthService, RefreshRequest, классы security и подключение токенов к frontend.

## 6. Что знать обоим: запуск и Docker

| Файл в корне | Назначение |

| `.env` | Локальные настройки и пароль администратора, пример находится в README |

Перед первым запуском создать `.env` по примеру из README, задать JWT_SECRET и ADMIN_PASSWORD. Если `.env` уже есть, использовать его. Ключ — минимум 32 байта. Администратор создаётся при первом запуске; при повторных запусках его пароль сверяется с ADMIN_PASSWORD и обновляется, если значение изменилось. В БД по-прежнему хранится только BCrypt-хеш. Для смены пароля изменить ADMIN_PASSWORD в `.env` и перезапустить приложение. Пароль — от 6 до 40 символов и не более 72 байт UTF-8; данные студентов сохраняются.

Без контейнера открыть `pom.xml` как проект в IntelliJ IDEA, выбрать JDK 17–25 и дождаться загрузки зависимостей Maven. Затем открыть `StudentsApplication.java` и запустить метод `main` зелёным треугольником.

В настройках Maven выбрать Bundled Maven. Рабочая папка запуска — корень `web_3`, где находятся `.env` и `pom.xml`. Остановка — кнопкой Stop в окне запуска. Подробная инструкция находится в README.

С установленным и запущенным Docker:

```sh
docker compose up --build
```

Приложение открывается на http://localhost:8080/. Для остановки:

```sh
docker compose down
```

Dockerfile имеет два этапа. Первый содержит Maven и JDK и собирает JAR. Второй содержит Java runtime и JAR, запускает `java -jar app.jar`. Maven и Java на хосте для такого запуска не требуются, нужен работающий Docker.

В Compose только один сервис: app. H2 находится внутри контейнера как файл `/app/data/students.mv.db`. Каталог `/app/data` подключён к именованному тому students-data. Том сохраняет студентов и пользователей после удаления и создания контейнера. `docker compose down` сохраняет том; добавление `-v` удалит его вместе с данными.

Локальный файл `data/students.mv.db` и том Docker — разные хранилища. Существующая локальная БД не копируется в образ. Первое открытие контейнерного приложения может показать пустой список — это новая БД.

`.env` передаётся при запуске контейнера и не копируется в образ. Порт приложения внутри контейнера — 8080; SERVER_PORT задаёт внешний порт на хосте. Публикация настроена только на localhost.

## 7. Общие вопросы и показ на защите

Оба должны знать: что такое JVM/JDK; чем Spring Boot отличается от Jakarta EE; как работают классы, интерфейсы и enum; зачем DI и аннотации; как HTTP-запрос превращается в ответ; где хранятся конфигурация и секреты.

JVM выполняет Java-байткод; JDK содержит средства разработки. Spring Boot помогает собрать и настроить серверное приложение. Jakarta EE — набор стандартов серверной Java, а не другое название Spring Boot. Здесь выбран Spring Boot, и используются Jakarta Persistence и Hibernate.

Показать по порядку:

1. Запуск и Swagger.
2. Регистрацию нового USER и вход.
3. Чтение списка под USER, отказ 403 при попытке изменения.
4. Вход ADMIN, создание, получение, PUT, PATCH и удаление студента.
5. Поиск, фильтры, сортировку и страницы.
6. Ошибку валидации и дублирующий ИСУ.
7. Обновление через refresh; access и refresh нельзя поменять местами.
8. Перезапуск и сохранность данных.

Первый участник объясняет шаги со студентами и БД, второй — вход, JWT, роли и 401/403. Docker и общую схему запроса объясняют оба.
